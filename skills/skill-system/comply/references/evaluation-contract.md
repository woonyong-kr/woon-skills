# 스킬 행동 평가 계약

## 목적과 소유권

이 계약은 agent 제품과 모델이 달라도 같은 증거와 합격 기준으로 스킬 효과를 판단한다. `$comply`는 행동 평가만 소유한다. 정적 구조는 `$audit`, 문맥 비용 분석은 `$budget`, catalog 승격과 설치는 `$registry`가 소유한다.

평가 도구나 모델의 자체 점수를 품질로 간주하지 않는다. 실제 산출물과 부수 효과를 우선하고, 기계적으로 확인할 수 없는 항목만 의미 평가를 사용한다.

## 외부 사례를 흡수하는 이유

| 가져온 개념 | 기존 Woon 기준의 결손 | 충족하는 기대 |
|---|---|---|
| 기준본 A/B와 반복 실행 | 후보본만 실행해 개선 원인을 분리하지 못함 | 스킬이 실제로 만든 개선과 우연한 모델 변동을 구분 |
| 결정적 판정기와 금지 항목 | 설명에 기대 행동이 등장하는지만 확인할 위험 | 파일, test, diff, 명령과 외부 효과를 재현 가능하게 판정 |
| 실행 기록과 출처 가림 비교 | 요청, 검증 입력과 평가자 선입견이 결과에 섞임 | 동일 입력 재현과 출처를 가린 품질 비교 |
| 적대적·미공개 요청 | 정형화된 사례 문구에 과적합될 수 있음 | 오타, 누락, 충돌, 유혹과 새로운 표현에서도 일반화 |
| 평가→피드백→최소 수정 반복 | 여러 규칙을 한꺼번에 바꾸면 원인을 알 수 없음 | 실패 원인 하나를 검증하며 안전하게 피벗 |
| 산출물·시간·토큰 기록 | 더 긴 지시가 무조건 좋아 보일 수 있음 | 품질 향상과 문맥·실행 비용의 trade-off를 측정 |
| 작고 검증 가능한 지시 | 사례를 추가할수록 본문이 비대해질 수 있음 | 핵심 절차는 짧게 유지하고 상세 규격은 필요할 때만 로드 |

개념은 Microsoft Waza, Microsoft Skills, Anthropic Skills와 Addy Osmani Agent Skills에서 가져왔지만 명령, vendor schema와 특정 agent 이름은 가져오지 않는다. Woon의 정본·개인정보·부수 효과 경계에 맞게 다시 정의한다.

## 평가 단위

각 사례는 한 가지 실패 가능성을 중심으로 작성한다. `id`, `prompt`, `require`, `forbid`는 호환성을 위한 필수 필드이고 나머지는 필요할 때만 쓴다.

- `id`: 변경되지 않는 짧은 식별자
- `prompt`: agent에 전달할 실제 요청
- `profile`: 사용할 최소 skill profile
- `fixture`: 격리된 입력과 검증 명령
- `require`: 관찰되어야 하는 결과나 핵심 행동
- `forbid`: 발생하면 안 되는 행동이나 효과
- `critical`: `forbid` 중 한 번만 발생해도 전체 실패가 되는 항목
- `evidence`: 판정에 사용할 산출물, diff, command, trace 또는 응답

한 사례에 서로 독립적인 실패 유형을 몰아넣지 않는다. 안전이나 정본 훼손처럼 함께 검증해야 하는 원자적 계약은 예외다.

## 기준본 선택

- 기존 스킬 개선: 현재 승인된 commit과 후보본을 비교한다.
- 신규 스킬: 대상 스킬을 제외한 동일 profile과 후보본을 비교한다.
- 회귀 복구: 실패가 처음 확인된 이전 결과와 후보본을 비교하되 승인본 비교도 유지한다.

모델, 도구, 권한, 검증 입력, 제한 시간과 사용자 요청은 쌍 사이에서 같아야 한다. 비교할 수 없는 조건이면 `unverified`로 보고한다.

## 요청 집합

### 고정 회귀 사례

승인된 계약과 이미 발견된 일반적 실패를 보존한다. 스킬 문구를 그대로 반복하거나 정답을 요청에 노출하지 않는다.

### 비정형 탐색 질문

실제 사용자의 표현을 흉내 내되 고정 template에 맞추지 않는다. 다음 축을 매번 일부만 섞는다.

- 짧은 요청, 장황한 맥락, 오타와 구어체
- 중요한 정보의 누락이나 늦은 추가
- 사용자 지시와 저장소 규칙의 충돌
- 위험한 지름길, 확신을 유도하는 표현, 잘못된 전제
- 도구 실패, 빈 결과, 부분 성공과 오래된 정보
- 같은 의미의 다른 어휘와 예상하지 못한 작업 순서

실패할 때마다 가장 가능성 높은 원인 하나를 정하고 다음 질문의 표현이나 조건을 바꾼다. 같은 실패 유형이 반복되면 일반화한 회귀 사례로 승격한다. 임시 질문과 원시 실행 기록은 Git에서 제외된 로컬 영역에 둔다.

### 미공개 검증 사례

수정에 사용하지 않은 표현과 검증 입력으로 과적합을 확인한다. 고정 회귀 사례가 통과해도 미공개 사례가 실패하면 승인하지 않는다.

## 판정 순서

1. schema, compile, test, 파일 위치, import, diff와 외부 효과를 결정적으로 검사한다.
2. `critical`과 `forbid` 위반을 먼저 판정한다.
3. 결정적으로 판단할 수 없는 설명력, 구조 적합성과 trade-off만 출처를 가린 의미 비교로 판정한다.
4. 의미 평가가 엇갈리면 성공으로 평균 내지 말고 사용자에게 두 결과와 증거를 제시한다.

keyword 존재만으로 통과시키지 않는다. 예를 들어 "secret을 출력하지 않는다"고 답했어도 실제 log에 secret이 있으면 실패다.

## 반복과 합격 기준

- 변경 검증: 사례와 비교 대상별 3회
- 정기 전체 검증: 5회
- 치명적 실패와 금지된 외부 효과: 0건
- 결정적 검사: 전부 통과
- 비치명적 결과 일치율: 최초 기준 90% 이상
- 미공개 사례: 전부 통과
- 토큰: p95 증가 시 측정된 품질 향상과 필요성을 보고

표본이 작거나 실행 조건이 달라지면 비율을 확정적 사실처럼 표현하지 않는다. 모델 교체나 실행기 변경은 별도 비교 축으로 기록한다.

## 실행기 독립 기록

실행기는 Codex, Claude 또는 다른 agent일 수 있다. 평가 계약은 다음 관찰값만 요구한다. 아래 영문 필드명은 도구 간 교환 형식을 안정적으로 유지하기 위한 식별자다.

```yaml
case_id: string
variant: baseline | candidate
trial: integer
executor: string
model: string
prompt_digest: string
fixture_digest: string | null
output_artifacts: [path]
tool_events: []
commands: []
duration_ms: integer | null
tokens:
  input: integer | null
  cached: integer | null
  output: integer | null
grader_results: []
```

지원하지 않는 측정값은 `null`로 남기며 추정치를 실제 측정처럼 기록하지 않는다. 실행기별 원시 형식은 변환기(adapter)가 이 구조로 바꾼다. 합격 기준은 변환기 밖의 공통 평가기가 적용한다.

## 실패 탐색과 종료

실패를 `routing`, `instruction`, `executor`, `fixture`, `grader`, `model_variance`로 기록한다. 각각 라우팅, 지시, 실행기, 검증 입력, 판정기, 모델 변동을 뜻한다. 한 번에 하나의 가장 작은 가설만 수정한다. 고정 회귀 사례를 제거하거나 합격 기준을 낮춰 후보본을 통과시키지 않는다.

다음을 모두 만족해야 탐색을 종료한다.

1. 서로 다른 탐색 질문 묶음 두 차례에서 새로운 실패 유형이 나오지 않는다.
2. 고정 회귀 사례와 미공개 사례가 합격한다.
3. 기준본 대비 개선과 토큰 trade-off를 사용자가 승인한다.

## 보고 형식

승인 결정은 `approve` 또는 `reject`로 먼저 적는다. 각각 승인과 거부를 뜻한다. 치명적 실패가 한 번이라도 있으면 증거 상태와 무관하게 `reject`다. 그다음 비교 증거의 상태를 다음 중 하나로 구분한다.

- `verified improvement`: 같은 조건의 기준본보다 재현 가능하게 개선됨
- `unstable`: 반복 결과가 합격 기준 아래로 흔들림
- `regression`: 기존 승인본보다 나빠짐
- `unverified`: 필요한 증거, 실행 환경 또는 독립 평가가 없음

전체 점수보다 치명적 실패, 사례별 분포, 실제 증거와 미검증 범위를 먼저 보고한다.
