# 문제 해결 흐름 계약

길거나 모순된 대화, 여러 번 방향을 바꾼 작업, 회고·troubleshooting 문서를 정리할 때만 읽는다.

## 증거 분류

| 종류 | 의미 | 근거 |
|---|---|---|
| 목표 | 원한 결과와 제약 | 사용자의 명시적 요청 |
| 관찰 | 실제로 확인한 상태 | 로그, diff, 파일, test, 화면, 사용자 확인 |
| 가설 | 원인을 설명하는 임시 판단 | 연결한 관찰과 반증 가능 조건 |
| 행동 | 조사·수정·되돌림 | 명령, tool call, 변경 기록 |
| 결과 | 행동 뒤의 변화 | 같은 조건의 재실행 또는 직접 확인 |
| 결정 | 선택한 방향과 버린 대안 | 드러난 근거와 trade-off |
| 통찰 | 다른 상황에도 쓸 규칙 | 적용·제외 조건과 증거 범위 |

근거 없는 기억, 의도 추측과 성공 추정은 관찰로 승격하지 않는다. private 값은 필요한 의미만 남기고 secret·개인 경로·원문 식별자는 제거한다.
근거의 양을 확인하지 못한 가설은 `미검증`이라고 쓰며, 증거가 전혀 없다고 단정하지 않는다.

## 연결 규칙

1. 사건에 `E1`, `E2`처럼 짧은 ID를 붙인다.
2. 가설은 지지·반박한 관찰 ID와 연결한다.
3. 전환점에는 `틀린 판단 → 바꾼 증거 → 달라진 행동`을 넣는다.
4. 해결은 `적용됨`, `부분 적용`, `제안`으로 구분한다.
5. 검증은 조건, 검사, 결과와 미검증 범위를 기록한다. prompt·인용 기록의 실행 결과는 `기록상 확인`이고, 현재 turn에서 agent가 실제 재실행한 결과만 `직접 확인`이다. 같은 결과를 확인·미검증으로 동시에 쓰지 않는다.
6. 같은 원인의 반복 증상은 병합하고, 다른 원인은 비슷해도 합치지 않는다.

## 전체 출력

이 문서를 읽었으면 결론·인과 원장·통찰을 각각 한 번 쓴다. 안전·정확성에 어긋나는 일부 요청이 있어도 그 부분만 제외하고 나머지 회고는 완성한다. 확인 범위와 미검증 범위를 생략하지 않는다.

### 결론

가장 중요한 해결, 현재 검증 상태와 통찰을 2~4문장으로 먼저 쓴다.

### 인과 원장

| ID | 종류 | 판단·행동·관찰 | 연결 근거 | 상태 |
|---|---|---|---|---|

`목표 → 증상 → 가설 → 조사 → 전환 → 해결 → 검증`을 이 표 한 번에 기록한다. 실수, 실패한 시도, 책임 경계와 수정도 해당 행에 넣는다. 시간순이 인과를 흐리면 원인별로 묶되 ID로 원래 순서를 보존한다. `확인됨`, `부분 확인`, `미검증`, `반증됨` 상태를 쓴다.
인접한 관찰·행동이 같은 전환을 설명하면 한 행으로 묶는다. 원장은 4~8행만 허용한다. 책임은 원인 행에 병합하고 남은 검증은 표에 넣지 않는다.

### 재사용할 통찰

> - **조건:** 언제 적용하는가
> - **신호:** 무엇을 먼저 확인하는가
> - **행동:** 어떤 순서로 대응하는가
> - **제외:** 언제 적용하지 않는가
> - **증거 수준:** 확인된 범위와 남은 검증

결론, 표, 통찰에 같은 사실을 반복하지 않는다. 결론은 결과, 표는 근거와 변화, 통찰은 재사용 조건만 소유한다. 실수나 책임을 확인하지 못했다면 새 절을 만들지 말고 관련 표 행에 `책임 미확인`으로 쓴다. 사용자가 승인하지 않은 저장·배포는 다음 행동에 넣지 않는다.
충돌한 사용자 요청을 설명해야 하면 산출물 밖 한 문장으로 끝내고 규칙 번호·원문을 인용하지 않는다.

제출 직전 전체 응답의 `직접 확인`을 다시 찾는다. 현재 turn의 tool·명령·화면 근거가 연결되지 않은 표현은 모두 `기록상 확인`으로 고친다.

## 실패 조건

- 시간순 요약만 있고 판단을 바꾼 증거가 없다.
- 사용자 요청과 모델 제안을 확정 사실로 취급한다.
- 반증된 판단을 현재 사실처럼 남긴다.
- 실행하지 않은 해결책을 완료로 표시한다.
- 문제를 사용자 실수로 돌리거나 책임을 추측한다.
- 민감한 원문과 식별자를 재노출한다.
- 같은 사실을 여러 절에서 반복한다.
- 요청 없이 `$archive`, publish, commit, push를 실행한다.
