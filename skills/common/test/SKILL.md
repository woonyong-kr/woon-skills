# Test

테스트는 어떤 잘못된 동작을 잡는지 증명한다.

## 변경 순서

1. 사용자에게 보이는 동작과 이 테스트가 잡아야 할 production 변경 하나를 적는다.
2. 기대값을 구현 코드와 독립적으로 계산해 가장 작은 테스트를 작성한다.
3. 구현 전에 테스트를 실행해 예상한 이유로 실패하는지 확인한다.
4. 통과에 필요한 최소 코드만 작성하고 좁은 테스트와 관련 suite를 실행한다.
5. 동작을 바꾸지 않고 구조를 정리한 뒤 다시 검증한다.

버그는 먼저 최소 재현으로 고정한다. 이미 구현한 코드에 뒤늦게 테스트를 붙이면 TDD라고 부르지 않는다. 현재 출력을 expected로 복사하지 말고 요구사항이나 독립 fixture에서 기대값을 도출한다. 수정 전 revision이나 안전한 임시 mutation에서 테스트가 실패하고 복구 후 통과하는지 확인하며, 독립 기대값을 확정할 수 없으면 release를 차단한다.

## 완료 경계

- 세금·결제·권한·데이터 변경 같은 핵심 동작은 자동 회귀 테스트 없이 merge·release·완료로 판정하지 않는다.
- checkpoint commit은 격리된 작업 branch에만 가능하다. 미검증 상태와 차단 조건을 명시하고 자동 회귀 테스트가 생기기 전에는 마감과 무관하게 release branch·merge 대상에 넣지 않는다.
- 사용자가 테스트 생략을 명시적으로 승인해도 검증된 품질로 표현하지 않고 영향과 후속 조건을 남긴다.
- framework 선택과 fixture 문법은 `$pytest`, `$spring-test` 등 언어·framework 스킬에 맡긴다.
- 전체 검증 계층과 완료 보고는 `$verify`가 소유한다.

테스트를 작성·수정하거나 mock·시간·동시성·파일 배치를 판단할 때 [테스트 설계 기준](references/design.md)을 읽는다.
