# Quality

## 최상위 실행 계약

1. **먼저 생각한다.** 성공 조건, 강제 제약, 확인된 사실, 가정과 선택의 trade-off를 구현 전에 분리한다. 선택에 따라 결과·복구 가능성·외부 영향이 달라지면 확인하고 확정 전에는 어느 분기도 실행하지 않는다. 결과를 바꾸지 않는 작은 빈칸은 가정을 밝힌 뒤 진행하되 그 가정을 검증된 사실로 표현하지 않는다.
2. **가장 단순하게 푼다.** 현재 요구와 계약을 만족하는 최소 구조를 선택하고, 확인되지 않은 미래를 위한 계층·설정·fallback을 추가하지 않는다. 단순화를 이유로 보안, 데이터 정합성, 호환성과 공개 계약을 제거하지 않는다.
3. **필요한 범위만 바꾼다.** 모든 변경 행을 요구사항이나 검증 근거에 연결하고 관련 없는 코드와 사용자 작업을 보존한다. 단, 동작을 완결하는 caller, schema, migration, 문서와 테스트까지 필요한 전파는 임의 정리로 보지 않는다.
4. **목표와 증거로 완료한다.** 작업 전에 수락 기준과 검증 방법을 정하고 통과할 때까지 수정한다. 새 동작·버그는 `$test`, 완료 주장은 `$verify`, 파괴적·외부 효과는 `$safety`에 맡긴다. 문서·설정처럼 test-first가 맞지 않으면 parse, build, audit, dry-run 등 산출물과 위험을 직접 증명하는 검증을 사용하고, 요구되었다는 이유만으로 의례적 테스트를 만들지 않는다. 실행하지 못한 항목은 `미검증`으로 남긴다.

## 적용 우선순위

1. 보안·안전 정책과 도구가 강제하는 제약을 지킨다.
2. `AGENTS.md`, 아키텍처 결정, 공개 API와 빌드 계약을 확인한다.
3. 강제 제약과 충돌하지 않으면 사용자가 명시한 구조와 합의한 결정을 요구사항으로 적용한다.
4. 언어·프레임워크 규칙을 적용하고, 남은 선택만 같은 역할의 기존 코드에서 확인한 일관된 관례로 결정한다.

상위 기준과 하위 기준이 충돌하면 사용자의 지시를 조용히 무시하지 않는다. 충돌 지점과 가능한 대안을 설명한다.

## 구조 판단

1. 변경할 동작의 책임, 상태 소유자, 부수 효과와 성공 조건을 정한다.
2. 위치는 책임과 의존성 방향으로 정하고 실제 경계가 없으면 새 계층·interface·wrapper를 만들지 않는다.
3. 배치 변경 전 강제 제약, `기존 → 변경`, 목표 tree, 호환성과 검증을 확정한다. 한두 파일만 담는 대칭형 계층 folder를 기본안으로 삼지 않는다.
4. 요청 범위의 일관성만 복구하고 관련 없는 변경은 보존한다.
5. 가장 좁고 결정적인 증거부터 실행하고 format→lint→type check→test 순으로 넓힌다.

배치·파일 분리·부수 효과를 판단할 때만 [상세 코딩 기준](references/coding-standards.md)을 읽고 이름은 `$naming`에 맡긴다. `.woon/repository.yaml`이 있거나 Woon 저장소 간 소유권을 판단할 때만 [Woon 저장소 규칙](references/woon-repository.md)을 읽는다.
