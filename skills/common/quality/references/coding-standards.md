# 상세 코딩 기준

이 문서는 언어와 프레임워크에 관계없이 사용하는 기본 설계 기준이다. 사용자가 명시한 구조를 취향으로 낮춰 해석하지 않는다. 강제 제약과 충돌하지 않는 한 명시된 구조를 구현 기준으로 삼는다.

## 목차

- 기준과 결정 형식
- 책임, 폴더와 파일 배치
- 함수·클래스·인터페이스
- 변경 범위, 부수 효과와 성능
- 완료 조건

## 기준을 선택하는 방법

다음 순서로 판단 근거를 고정한다.

1. 사용자가 지정하거나 대화에서 합의한 구조와 이름을 기록한다.
2. 저장소가 강제하는 경로, 공개 API, 직렬화 형식과 프레임워크 계약을 찾는다.
3. 같은 역할을 수행하는 파일을 찾고, 두 곳 이상에서 동일하게 나타나는 규칙만 기존 관례로 인정한다.
4. 기존 사례가 서로 다르면 관례가 없는 것으로 판단하고 이 문서의 기준을 적용한다.
5. 선택한 폴더, 파일과 이름이 어떤 책임과 제약에서 나온 것인지 설명할 수 있어야 한다.

사용자 지시와 강제 제약이 충돌하면 한쪽을 임의로 버리지 않는다. 충돌하는 규칙, 영향을 받는 파일과 호환 가능한 대안을 먼저 제시한다.

## 필수 결정 형식

배치나 이름을 바꾸기 전에 다음 결과를 만든다. 실제 수정 작업에서는 작업 전 판단으로 사용하고 완료 보고에서는 실제 변경 결과로 갱신한다.

1. 강제 제약: 발견한 규칙과 찾지 못한 규칙을 구분한다.
2. 사용자 요구: 지정된 구조, 보존할 동작과 변경 허용 범위를 적는다.
3. 책임 표: 각 구성 요소의 책임, 소유 상태와 부수 효과를 적는다.
4. 변경 매핑: `기존 경로·이름 → 새 경로·이름 → 변경 이유`를 한 줄씩 적는다.
5. 목표 트리: 새 폴더와 파일 구조를 표시한다.
6. 호환성: 공개 import, 호출 signature, HTTP·JSON, 직렬화, reflection과 저장 형식 중 유지할 계약을 적는다.
7. 검증: 저장소에서 실제로 확인한 명령과 각 명령이 증명하는 항목을 적는다.

`깔끔하게`, `읽기 쉽게`, `일관되게`만으로 결정을 정당화하지 않는다. 책임, 계약, 호출자 또는 측정 가능한 탐색 비용과 연결한다.

## 책임 확정

코드를 배치하기 전에 다음 네 항목을 한 문장씩 정한다.

- 책임: 이 코드가 보장하는 동작 또는 정책
- 소유 상태: 읽거나 변경하는 데이터와 그 생명주기의 소유자
- 부수 효과: 파일, 데이터베이스, 네트워크, 프로세스와 외부 상태 변경
- 성공 조건: 테스트나 관찰 가능한 결과로 확인할 수 있는 완료 상태

두 동작의 책임, 상태 소유자 또는 변경 이유가 다르면 같은 모듈이나 클래스에 합치지 않는다.

## 코드와 폴더 배치

| 변경 대상 | 기본 위치 | 금지하는 배치 |
| --- | --- | --- |
| 업무 규칙, 불변 조건, 값 계산 | 해당 기능의 도메인 소유자 | UI, 데이터베이스 또는 프레임워크 모듈 |
| 여러 도메인 동작의 순서와 트랜잭션 | 애플리케이션 유스케이스 | 엔티티, 컨트롤러 또는 저장소 구현 |
| HTTP, CLI, 메시지 입력 변환 | 입력 경계 또는 인바운드 어댑터 | 도메인 정책 내부 |
| 데이터베이스, 외부 API, 파일시스템 연결 | 아웃바운드 어댑터 또는 기반 구조 | 도메인 정책 내부 |
| 외부 형식의 파싱과 형식 검증 | 입력을 처음 받는 경계 | 여러 내부 계층에 중복 |
| 업무 불변 조건 검증 | 해당 도메인 타입 또는 정책 | 컨트롤러에만 존재하는 조건문 |
| 설정값과 설정 스키마 | 값을 소비하고 검증하는 구성 요소 | 저장소 루트의 임의 파일 |
| 여러 호출자가 공유하는 순수 동작 | 동일한 의미의 도메인 모듈 | `common`, `utils`, `helpers` 같은 포괄 폴더 |

저장소가 계층 구조를 사용하지 않으면 새 계층 전체를 만들지 말고 같은 책임을 소유한 기존 기능 모듈에 둔다.

하위 폴더는 다음 중 하나일 때만 만든다.

- 프레임워크, 빌드 도구 또는 공개 API가 경로를 강제한다.
- 현재 변경이 끝났을 때 같은 책임의 production 파일이 3개 이상 존재한다.
- 같은 이름의 타입이 충돌하거나 package/module 접근 경계가 필요하다.

위 조건이 없고 역할별 파일이 1~2개뿐이면 기능 폴더를 평평하게 유지한다. `web/application/domain/persistence`처럼 각 폴더에 파일 하나만 넣는 대칭형 계층을 만들지 않는다. 파일 수가 아니라 실제 경계를 표현하기 위해 폴더가 필요한 예외는 강제 제약 또는 접근 경계로 증명한다.

## 파일 분리와 선언 위치

다음 중 하나에 해당하면 별도 파일로 분리한다.

- 독립된 공개 계약이나 최상위 타입을 가진다.
- 상태 소유자 또는 변경 이유가 기존 파일과 다르다.
- 프레임워크나 언어가 파일 경계를 강제한다.
- 기존 파일을 읽을 때 서로 무관한 두 흐름을 오가야 한다.

한 공개 동작에만 종속된 작은 보조 함수는 그 동작의 소유자와 같은 파일에 둔다. 언어별 규칙이 없으면 상수와 타입 → 공개 진입점 → 내부 보조 함수 순으로 배치하고, 내부 보조 함수는 사용하는 공개 동작과 가까운 묶음으로 유지한다. 테스트는 구현 계층 이름보다 검증하는 기능과 공개 동작을 기준으로 배치한다.

## 함수·클래스·인터페이스

- 함수는 관찰 가능한 결과 하나를 책임지고 입력, 출력, 오류와 부수 효과를 이름 또는 계약에서 확인할 수 있게 한다.
- 오류 조건을 먼저 끝내는 보호 절(guard clause)로 정상 흐름의 중첩을 줄인다.
- 클래스는 식별성, 불변 조건, 생명주기 또는 다형적 행동 중 하나를 소유할 때 만든다.
- 인터페이스는 실제 교체 대상, 외부 경계 또는 소비자 주도 테스트 경계가 있을 때만 만든다.
- 구현체가 하나이고 교체·격리 필요성이 없으면 형식적인 인터페이스와 래퍼를 추가하지 않는다.
- 상태 불변 조건을 다루는 함수는 상태 소유 타입에 두고, 여러 소유자를 조정하거나 I/O 경계를 여는 함수는 유스케이스에 둔다.
- 순수 계산을 위해 클래스 상태가 필요하지 않으면 정적 유틸리티 클래스보다 의미 있는 모듈 함수나 값 타입을 검토한다.

## 단순성과 변경 범위

- 요청하지 않은 기능, 설정 가능성 또는 미래 확장 지점을 추가하지 않는다.
- 한 번만 사용하는 코드를 위해 추상화(abstraction)를 만들지 않는다.
- 입력, 상태 전이 또는 외부 계약에서 도달 경로를 설명할 수 없는 분기를 추측해서 추가하지 않는다.
- 요청과 관계없는 인접 코드, 주석과 포맷을 정리하지 않는다.
- 기존 죽은 코드(dead code)는 발견 사실만 알린다. 이번 변경 때문에 사용되지 않게 된 import, 변수와 함수만 제거한다.
- 모든 변경한 줄을 사용자의 요청이나 그 요청에 필요한 검증과 연결할 수 있어야 한다.

사용자가 구조 정리나 일관성 복구를 요청했다면 그 범위의 이동·이름 변경·호출자 수정은 관련 변경이다. 다만 한 번에 책임 단위 하나를 이동하고 공개 API 호환성과 테스트를 확인한 뒤 다음 단위로 진행한다.

구현이 필요 이상으로 커졌다면 더 작은 해법을 다시 찾는다. 단순함은 줄 수만 줄이는 것이 아니라 책임, 상태 변경과 실패 경로를 더 쉽게 이해할 수 있게 만드는 것이다.

## 데이터와 부수 효과

- 소유권 경계에서는 불변 데이터 흐름을 우선한다. 공유 컬렉션(collection)을 정렬하거나 변환하기 전에 복사한다.
- 성능 또는 API 계약 때문에 직접 변경(mutation)이 필요하면 변경 범위를 작고 명시적으로 유지한다.
- I/O, 네트워크 호출, 쓰기, 전역 상태 또는 프로세스 실행을 순수 함수처럼 보이는 보조 함수(helper) 뒤에 숨기지 않는다.
- 원래 오류를 원인으로 보존하고, 의미를 아는 경계에서 행동 가능한 맥락을 추가한다.
- 잘못된 외부 입력은 영속 상태 또는 공유 상태를 바꾸기 전에 거부한다.
- 오류를 기록한 뒤 같은 경계에서 다시 중복 기록하지 않는다.
- 실패를 빈 값이나 기본값으로 조용히 바꾸지 않는다. 계약상 허용된 대체 동작이면 조건과 관찰 방법을 명시한다.

## 동시성과 성능

- 작업이 서로 독립적이고 동시 실행 제한과 부분 실패를 감당할 수 있을 때만 병렬로 실행한다.
- 병렬 실행 전에 전체 실패와 부분 성공 중 어떤 정책을 사용할지, 결과 순서를 보존할지, 취소와 재시도를 어떻게 처리할지 정한다.
- 캐시, 인덱스, 묶음 처리와 병렬 처리는 계약상 필요하거나 병목이 측정됐을 때만 추가한다.
- 성능 개선을 주장할 때는 관련 측정값과 측정 조건을 남긴다.

## 근거의 경계

KISS, DRY, YAGNI, 불변성과 가독성은 검토 기준이지 모든 상황에 적용되는 경험적 보장이 아니다.

- 현재 코드, 테스트, 프로파일링, 장애 또는 검토 이력이 더 구체적인 규칙을 입증하기 전에는 명확성을 우선한다.
- 반복된 동작과 변경 경계를 이해한 뒤 중복을 추출한다. DRY를 기계적으로 적용하지 않는다.
- 정책상 기본값과 실제 측정 결과를 구분한다. 결함률, 검토 시간, 렌더링 비용 또는 쿼리 비용을 추정해 사실처럼 말하지 않는다.

## 완료 조건

완료를 보고하기 전에 다음을 확인한다.

- 선택한 폴더와 파일이 책임·소유권 규칙과 일치한다.
- 한두 파일만 담는 새 대칭형 계층 폴더가 없거나 예외 근거가 기록돼 있다.
- 사용자가 지정하거나 합의한 구조를 구현했으며, 따르지 못한 항목은 이유를 밝혔다.
- 모든 변경한 줄이 요청한 동작 또는 필요한 검증과 연결된다.
- 관련 없는 사용자 변경이 그대로 보존된다.
- 제공되는 포매터, 린터, 타입 검사와 테스트를 관련 범위에서 실행했다.
- 가능하면 사용자에게 보이는 동작도 확인했다.
- 실행하지 않은 통합, E2E, 배포 또는 운영 환경 검증을 명시했다.
