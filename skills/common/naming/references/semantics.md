# 이름 의미 기준

이 문서는 이름이 약속해야 하는 의미와 선택 절차를 정의한다. 선호하거나 피할 실제 단어는 [사용자 어휘](vocabulary.md)가 소유하고, 대소문자와 파일·package/module 표기는 언어 스킬이 소유한다.

## 목차

- 판단 순서와 이름 구성
- 선언 종류별 기준
- 존재 여부·개수·오류 계약
- 동사와 상태 전이
- 역할과 경계 접미사
- 인터페이스와 구현체
- Boolean·컬렉션·단위·시간
- 약어와 대칭 이름
- 공개 이름 변경
- 완료 점검

## 판단 순서와 이름 구성

새 이름은 다음 순서로 정한다.

1. 소유 도메인과 대상이 무엇인지 정한다.
2. 호출자가 관찰하는 행동, 결과, 오류와 부수 효과를 적는다.
3. 단건·복수, 필수·선택, 시점·기간과 단위를 구분한다.
4. 함수는 `행동 + 도메인 대상`, 타입은 `도메인 대상 + 역할`을 기본형으로 만든다.
5. 같은 범위의 다른 이름과 구분할 때만 의미 한정어 하나를 추가한다.
6. [사용자 어휘](vocabulary.md)의 선호·제한·금지 표현을 적용한다.
7. 언어 스킬의 표기법과 저장소의 공개 계약을 적용한다.

이름은 가능한 한 짧게 하되, 길이 자체를 목표로 줄이지 않는다. 같은 범위에서 뜻이 하나로 결정되는 가장 짧은 이름을 선택한다.

- 매개변수가 설명하는 조건, 단위와 구현 단계를 함수명에 반복하지 않는다.
- `and`, `with`, `using`으로 여러 구현 단계를 이어 붙이지 않는다.
- 여러 행동을 하나의 도메인 결과로 설명할 수 없으면 함수를 분리한다.
- `process data`처럼 짧지만 대상과 결과가 불명확한 이름은 허용하지 않는다.
- 저장소 이름, namespace와 상위 타입이 이미 제공하는 문맥을 하위 이름에 반복하지 않는다.
- 하나의 유스케이스를 실행하는 타입은 `행동 + 도메인 대상 + 역할`을 사용한다. 직접적인 동사가 있으면 `Creation`, `Processing` 같은 명사화로 길게 만들지 않는다.
- 함수의 도메인 대상은 기본적으로 호출자가 받는 결과나 실제로 변경되는 대상을 사용한다. database·API·filesystem 같은 source 이름은 결과가 아니라 여러 source를 구분해야 할 때만 한정자로 추가한다.

예시:

- 함수 의미 `sort and filter reports by minimum score`보다 `rank reports`; 조건과 단위는 매개변수로 표현
- user service 문맥의 `user service create user`보다 `create user`
- create-user 유스케이스 타입은 `user creation service`보다 `create user service`
- order repository 문맥의 `find order by order id`보다 저장소 관례가 허용하는 `find by id`
- inventory API에서 stock records를 가져오면 `fetch inventory`보다 `fetch stocks`; source 구분이 필요할 때만 inventory 한정자를 추가

마지막 예시는 해당 언어와 저장소가 repository 문맥의 생략을 허용할 때만 적용한다.

## 선언 종류별 기준

| 대상 | 기본 의미 | 확인할 항목 |
| --- | --- | --- |
| 타입·클래스 | 책임이나 정체성을 가진 명사 | 소유 상태, 불변 조건, 생명주기 |
| 인터페이스·port | 소비자가 요구하는 능력이나 외부 경계 | 소비자, 교체 대상, 테스트 경계 |
| 함수·메서드 | 관찰 가능한 행동과 도메인 대상 | 결과, 오류, 부수 효과 |
| 변수·필드 | 현재 담긴 값의 역할 | 단건·복수, 단위, nullable 여부 |
| 상수 | 변하지 않는 정책값이나 제한 | 적용 범위, 단위, 기준 시점 |
| Boolean | 긍정문으로 답할 수 있는 질문 | `true`의 정확한 의미 |
| 컬렉션 | 요소를 드러내는 복수 명사 | 순서, 중복, 변경 가능성 |
| map·index | 값과 key의 관계 | 무엇을 무엇으로 찾는지 |
| callback | 발생 시점이나 완료 행동 | 호출 조건, 성공·실패 경계 |
| event | 이미 발생한 도메인 사실 | 과거형 의미, 발생 주체 |
| 오류 타입 | 실패한 동작이나 위반한 계약 | 원인, 복구 가능성, 경계 |

지역 변수는 가까운 범위에서만 의미가 완전하다면 짧게 쓸 수 있다. 공개 타입, API, 설정 key와 저장 형식은 사용처가 멀고 호환 비용이 크므로 축약보다 명시성을 우선한다.

## 존재 여부·개수·오류 계약

이름은 반환 계약을 숨기지 않는다.

- 결과가 없을 수 있고 부재가 정상이라면 선택 조회 의미를 사용한다.
- 반드시 존재해야 하고 부재가 오류라면 필수 조회 의미를 사용한다.
- 여러 결과를 반환하면 복수 대상 또는 컬렉션 의미를 사용한다.
- 개수만 반환하면 대상을 복수형으로 만들기보다 `count` 의미를 사용한다.
- 존재 여부만 반환하면 전체 객체를 반환하는 것처럼 이름 짓지 않는다.
- 실패를 빈 값으로 바꾸는 함수는 일반 조회 이름을 사용하지 않는다. 허용된 fallback이면 이름이나 계약에 드러낸다.
- `try` 계열은 실패를 예외로 던지지 않고 성공 여부를 별도로 전달할 때만 사용한다.

`find`, `get`, `require`, `list`, `exists`의 구체적인 선호는 사용자 어휘를 따른다. 언어·프레임워크가 같은 단어에 강한 관례를 부여하면 공개 API에서는 그 관례를 우선하고 내부 이름에서 의미를 보완한다.

## 동사와 상태 전이

| 의미 | 이름이 약속하는 계약 |
| --- | --- |
| `calculate` | 외부 상태를 바꾸지 않고 공식이나 규칙으로 값을 계산한다. |
| `derive` | 이미 확인된 값에서 새로운 의미를 결정적으로 도출한다. |
| `build` | 메모리 안에서 여러 입력을 조립해 새 결과를 만든다. |
| `create` | 새 도메인 객체나 자원을 만든다. 영속화 여부는 계약에 명시한다. |
| `find` | 결과가 없을 수 있는 단건 조회다. |
| `get`·`require` | 대상이 존재해야 하며 부재를 오류로 취급한다. 단순 접근자는 언어 관례를 따른다. |
| `list` | 0개 이상인 컬렉션을 반환한다. |
| `load` | 파일, 저장소 또는 이미 구성된 local source에서 읽는다. |
| `fetch` | network·IPC 같은 원격 경계를 넘어 가져온다. |
| `parse` | 외부 표현을 구조화된 값으로 바꾸고 잘못된 형식을 거부한다. |
| `format` | 구조화된 값을 사람이 읽거나 표시할 표현으로 만든다. |
| `serialize` | 구조화된 값을 저장·전송 형식으로 인코딩한다. |
| `deserialize` | 저장·전송 형식을 구조화된 값으로 복원하고 형식을 검사한다. |
| `map` | 의미를 유지하며 대응하는 다른 표현으로 옮긴다. |
| `convert` | 단위, 표현 또는 타입을 명시적으로 바꾼다. |
| `normalize` | 여러 허용 표현을 하나의 정규형으로 만든다. |
| `validate` | 상태를 바꾸지 않고 규칙 위반을 수집하거나 오류로 보고한다. |
| `check` | 한 조건을 확인하고 Boolean이나 간단한 판정을 반환한다. |
| `ensure` | 조건을 확인하고 필요하면 멱등적으로 상태를 만족시킨다. |
| `add` | 기존 컬렉션이나 소유자에 구성원을 추가한다. |
| `register` | 이후 조회·발견·호출할 수 있도록 등록한다. |
| `update` | 기존 대상의 일부 속성을 변경한다. |
| `replace` | 기존 대상을 새 표현으로 전체 교체한다. |
| `remove` | 컬렉션·관계·화면에서 제외한다. 영구 삭제를 자동으로 뜻하지 않는다. |
| `delete` | 영속 대상을 제거한다. 복구 가능 여부는 계약에 명시한다. |
| `archive` | 활성 상태에서 보존 상태로 옮기며 복구 가능성을 유지한다. |
| `restore` | 보존·삭제 대기 상태에서 사용 가능한 상태로 되돌린다. |
| `publish` | 외부 소비자가 볼 수 있는 상태로 전환한다. |

읽기처럼 보이는 이름이 write, network, process 실행이나 전역 상태 변경을 숨겨서는 안 된다. 이름만으로 모든 효과를 표현할 수 없다면 타입·module 경계와 문서화된 계약으로 보완한다.

쌍을 이루는 상태 전이는 같은 추상화 수준을 사용한다.

- `start` ↔ `stop`
- `open` ↔ `close`
- `enable` ↔ `disable`
- `activate` ↔ `deactivate`
- `attach` ↔ `detach`
- `subscribe` ↔ `unsubscribe`
- `publish` ↔ `unpublish` 또는 도메인상 `withdraw`
- `archive` ↔ `restore`

반대 동작이 실제로 완전한 역연산이 아니라면 억지로 대칭 이름을 만들지 않는다.

## 역할과 경계 접미사

역할 접미사는 실제 책임을 증명할 때만 사용한다.

| 접미사 | 허용하는 책임 |
| --- | --- |
| `Service` | 하나의 유스케이스 또는 여러 소유자의 흐름 조정 |
| `Manager` | 자원의 생성부터 종료까지 전체 생명주기 관리 |
| `Handler` | 한 종류의 command, request 또는 event 처리 |
| `Controller` | HTTP·UI·CLI 같은 입력 경계와 응답 변환 |
| `Client` | 특정 원격 API나 protocol 호출 |
| `Gateway` | 외부 subsystem과의 고수준 통합 경계 |
| `Repository` | 도메인 객체나 aggregate의 저장·조회 계약 |
| `Store` | key/value, session, document 같은 일반 저장소 |
| `Cache` | 다시 만들 수 있는 비정본 임시 저장소 |
| `Factory` | 생성 전략을 캡슐화해 완성된 객체 반환 |
| `Builder` | 여러 단계로 구성되는 객체 조립 |
| `Provider` | 값, dependency 또는 capability 공급 |
| `Adapter` | 한 경계의 계약을 다른 구현이나 형식에 연결 |
| `Mapper` | 두 표현 사이의 필드·의미 대응 |
| `Validator` | 재사용되는 검증 규칙 집합 |
| `Policy` | 업무 결정을 내리는 규칙 집합 |
| `Strategy` | 같은 계약 아래 교체 가능한 알고리즘 |
| `Scheduler` | 실행 시각과 반복 정책 결정 |
| `Worker` | queue나 scheduler가 전달한 작업 실행 |

역할이 하나의 함수로 충분하면 접미사 타입을 만들지 않는다. 접미사를 제거했을 때 책임을 설명할 수 없다면 타입 자체의 경계가 불명확한 것이다.

한 유스케이스만 소유하는 `Service`는 `행동 + 대상 + Service`로 짓는다. 여러 유스케이스를 묶는 facade가 실제로 필요할 때만 `대상 + Service`를 사용한다.

경계 타입은 실제 변환·검증·보안·생명주기 차이가 있을 때만 나눈다.

- `Request`, `Response`: HTTP나 message 같은 전송 경계 계약
- `Command`, `Query`: 전송 형식과 분리된 application 입력 계약
- `Event`: 이미 발생한 사실
- `Entity`: identity와 영속 생명주기를 직접 표현하는 타입
- `Result`: 성공 결과와 실패 정보가 하나의 명시적 계약일 때 사용
- `Config`: 해석·검증이 끝난 구성
- `Options`: 호출자가 선택적으로 제공하는 조정값
- `Context`: 한 작업 범위에서 함께 전달되는 실행 문맥

필드가 같다는 이유만으로 경계별 타입을 복제하지 않는다. `Request`와 `Command`처럼 경계에 따라 달라지는 이름은 annotation, 생성 위치와 실제 호출자를 확인한다. 근거가 없으면 하나를 추측하지 말고 조건부 후보로 제시한다.

## 인터페이스와 구현체

- 인터페이스는 소비자가 요구하는 능력이나 외부 경계를 표현한다.
- 이름은 구현 기술보다 소비자가 사용하는 도메인 capability를 우선한다.
- 구현체는 `Default`나 `Impl`보다 전략, 저장 기술 또는 외부 시스템 차이를 표현한다.
- 구현체가 하나이고 교체·격리 경계가 없으면 이름을 위해 인터페이스를 만들지 않는다.
- `Port`, `Adapter`를 관례적으로 모든 이름에 붙이지 않는다. package/module 문맥만으로 경계가 분명하면 도메인 이름을 유지한다.
- mock이나 fake는 production 구현체 이름을 흉내 내지 말고 테스트에서 보장하는 행동을 드러낸다.

예시:

- `PaymentRepositoryImpl`보다 `PostgresPaymentRepository`
- `NotificationServiceImpl`보다 `EmailNotificationSender`
- `IUserRepository`보다 해당 언어 관례에 맞는 `UserRepository`

## Boolean·컬렉션·단위·시간

Boolean 이름은 긍정문으로 만들고 `true`가 무엇을 뜻하는지 하나로 고정한다.

- 현재 상태: `is...`
- 소유·포함: `has...`
- 능력·권한: `can...`
- 정책상 권고: `should...`
- 존재 여부: `...Exists` 또는 언어 관례에 맞는 존재 동사

`notDisabled`, `noErrorsFound` 같은 이중 부정을 피한다. 성공과 유효성을 한 Boolean에 합치지 않는다.

컬렉션과 수치 이름은 해석 정보를 보존한다.

- 컬렉션은 요소의 복수형을 사용한다.
- map은 `값 + By + Key` 관계를 드러내거나 언어의 표준 map 문맥을 따른다.
- 총수는 `count`, 순번은 `index`, 식별자는 `id`, 측정값은 필요한 단위를 구분한다.
- 시간이 시점이면 `...At`, 기간이면 `...Duration`이나 실제 단위를 사용한다.
- 크기·제한·timeout은 해석이 달라질 수 있으면 `Bytes`, `Seconds`, `Milliseconds` 같은 단위를 포함한다.
- 범위는 `start/end`, 변환은 `source/target`, 비교는 `previous/current`처럼 대칭 쌍을 사용한다.

## 약어와 대칭 이름

- 언어와 도메인에서 널리 쓰이는 약어만 사용한다.
- 같은 범위에서 약어와 전체 단어를 섞지 않는다.
- 한 글자 이름은 짧은 수학식, 좌표, index 또는 관용적인 매우 좁은 scope로 제한한다.
- 공개 API에서는 팀 밖 소비자가 해석하지 못할 내부 약어를 사용하지 않는다.
- 이름 충돌을 피하려고 숫자나 임의 접미사를 붙이지 않는다. 책임이나 범위를 다시 구분한다.
- 입력과 출력, 이전과 이후, 부모와 자식처럼 쌍을 이루는 이름은 같은 문법 구조를 사용한다.

약어의 대소문자는 언어 스킬이 결정한다. 이 문서는 약어 사용 여부와 의미만 결정한다.

## 공개 이름 변경

이름을 바꾸기 전에 다음 사용처를 검색한다.

1. source와 test의 직접 호출·import
2. package export와 public API 문서
3. JSON·database·event·config의 문자열 key
4. reflection, annotation, dependency injection과 plugin 등록
5. shell script, CI, deployment와 외부 저장소 소비자

변경 결과는 `기존 이름 → 새 이름 → 의미 차이 → 호환 방법`으로 기록한다.

- 내부 이름은 모든 호출자를 함께 바꿀 수 있으면 한 번에 변경한다.
- 공개 계약은 실제 소비자를 확인하고 deprecation, alias, adapter 또는 migration 중 가장 작은 방법을 선택한다.
- signature와 runtime contract가 같으면 alias를 우선 검토한다.
- 입력·출력·오류 계약이 달라지면 wrapper나 adapter로 변환 지점을 드러낸다.
- 이름만 남기기 위한 영구 wrapper는 만들지 않고 제거 조건을 기록한다.

## 완료 점검

- 이름만 읽고 대상, 행동과 역할을 설명할 수 있다.
- 단건·복수, 필수·선택과 Boolean 의미가 일치한다.
- 함수명에 매개변수와 구현 단계를 반복하지 않았다.
- 포괄 이름을 다른 포괄 이름으로 치환하지 않았다.
- 읽기 이름이 write·network·process 부수 효과를 숨기지 않는다.
- 역할 접미사는 실제 책임이나 경계로 증명된다.
- 언어 표기와 저장소의 같은 역할 이름이 일관된다.
- 공개 이름의 호출자와 문자열 기반 계약을 확인했다.
- 근거 없는 경계 타입, alias, interface와 adapter를 추가하지 않았다.
