# 사용자 어휘

이 문서는 사용하면서 바뀌는 선호 표현의 단일 정본이다. 이름의 의미 계약은 [이름 의미 기준](semantics.md), 표기법은 언어 스킬을 따른다.

## 목차

- 적용 우선순위와 상태
- 조회와 존재
- 생성·변경·생명주기
- 변환·계산·검증
- 경계와 역할 명사
- 금지하거나 제한하는 표현
- 약어와 짝 이름
- 저장소·도메인별 어휘
- 어휘 추가·변경 절차

## 적용 우선순위와 상태

다음 순서로 어휘를 선택한다.

1. 사용자가 이번 작업에서 명시한 단어
2. 이 문서의 `확정` 항목
3. 저장소가 공개 계약이나 domain glossary로 강제하는 단어
4. 이 문서의 `기본` 항목
5. [이름 의미 기준](semantics.md)에 맞는 가장 짧은 후보

| 상태 | 의미 |
| --- | --- |
| `확정` | 사용자가 명시적으로 선택했으며 전역 기본으로 적용 |
| `기본` | 별도 선호나 저장소 계약이 없을 때 적용 |
| `제한` | 표에 적힌 구체적인 책임일 때만 사용 |
| `금지` | 새 이름에 사용하지 않음 |
| `폐기` | 기존 호환 기간에만 남기고 새 코드에서는 대체 |

현재 추가된 일반 표현은 `기본`이다. 사용자가 선호를 밝히면 해당 행을 `확정`으로 바꾸고 충돌하는 행을 함께 정리한다.

## 조회와 존재

| 상태 | 상황 | 선호 표현 | 피할 표현 | 적용 규칙 |
| --- | --- | --- | --- | --- |
| 기본 | 값이 없을 수 있는 단건 조회 | `find` | 무조건 `get` | 부재를 정상 결과로 표현 |
| 기본 | 값이 반드시 필요한 단건 조회 | `require` | `find` 후 숨은 예외 | 부재가 오류임을 이름에 표현 |
| 기본 | 언어·framework의 표준 접근자 | `get` | 인위적인 `require` | 단순 필드·key 접근 관례 유지 |
| 기본 | 0개 이상인 여러 값 조회 | `list` | `getAll`, `findAll`의 무조건 사용 | 저장소 표준 API가 있으면 그 관례 우선 |
| 기본 | 존재 여부만 확인 | `exists` | 전체 객체 조회를 암시하는 이름 | Boolean만 반환 |
| 기본 | 개수 조회 | `count` | `size`의 무조건 사용 | `size`는 메모리 collection 관례에 제한 |
| 기본 | 파일·local 저장소·구성에서 읽기 | `load` | 원격 호출에 `load` | local 또는 추상 저장소 I/O |
| 기본 | 원격 API·network에서 읽기 | `fetch + 반환 대상` | network 호출에 `get`만 사용 | 원격 부수 효과와 호출자가 받는 결과를 드러냄; source는 구분이 필요할 때만 한정 |
| 기본 | stream·iterator로 순회 | `iterate`, `stream` | collection 반환을 암시하는 `list` | 실제 lazy 계약이 있을 때만 사용 |

`get`과 `require`가 모두 가능한 내부 API라면 부재 오류를 가장 분명히 드러내는 `require`를 우선한다. 공개 framework API를 감싸기 위해 이름만 바꾸는 wrapper는 만들지 않는다.

## 생성·변경·생명주기

| 상태 | 상황 | 선호 표현 | 피할 표현 | 적용 규칙 |
| --- | --- | --- | --- | --- |
| 기본 | 새 독립 객체·자원 생성 | `create` | 모든 생성에 `make` | 저장 여부는 계약으로 보완 |
| 기본 | 여러 입력으로 메모리 결과 조립 | `build` | 단순 생성에 `builder` 타입 추가 | 단계적 조립이 필요할 때 사용 |
| 기본 | 기존 소유자·collection에 추가 | `add` | 새 독립 자원에 `add` | 소유 관계가 있을 때 사용 |
| 기본 | 이후 발견·호출할 수 있게 등록 | `register` | 일반 저장에 `register` | registry 의미가 있을 때 사용 |
| 기본 | 기존 대상 일부 변경 | `update` | 부분 변경에 `replace` | 변경 가능한 필드를 계약으로 제한 |
| 기본 | 전체 값 교체 | `replace` | 전체 교체에 `update` | 이전 값이 새 값으로 대체됨 |
| 제한 | create/update를 모두 허용하는 영속화 | `save` | 계약 불명확한 범용 쓰기 | repository·framework가 upsert를 명시할 때만 사용 |
| 기본 | 관계·collection에서 제외 | `remove` | 영구 삭제를 뜻하는 경우 | 원본 존재 가능성을 유지 |
| 기본 | 영속 대상을 제거 | `delete` | 복구 가능한 보관에 `delete` | 파괴 범위와 복구 가능성 확인 |
| 기본 | 복구 가능한 비활성 보관 | `archive` | soft delete를 무조건 `delete` | 보존 상태와 복구 계약 필요 |
| 기본 | 보관 상태에서 복구 | `restore` | 의미가 다른 `recover` | archive의 대응 동작 |
| 기본 | 외부 공개 상태로 전환 | `publish` | 단순 저장에 `publish` | 실제 가시성 변화가 있어야 함 |
| 기본 | 실행 생명주기 시작·종료 | `start`·`stop` | `run`·`kill`의 포괄 사용 | 자원 생명주기를 소유할 때 사용 |
| 기본 | 자원 획득·반납 | `open`·`close` | 비대칭 동사 | handle이나 connection 경계에 사용 |
| 기본 | 기능 상태 전환 | `enable`·`disable` | `toggle` | 목표 상태를 명시하고 멱등적으로 적용 |

`toggle`은 현재 상태에 따라 결과가 달라 재시도와 자동화가 불안정하므로 UI 이벤트 내부가 아니면 피한다.

## 변환·계산·검증

| 상태 | 상황 | 선호 표현 | 피할 표현 | 적용 규칙 |
| --- | --- | --- | --- | --- |
| 기본 | 정렬해 순위를 부여 | `rank` | 정렬·필터 단계를 모두 나열한 이름 | 구현 단계보다 도메인 결과 표현 |
| 기본 | 공식·업무 규칙으로 수치 계산 | `calculate` | 포괄적인 `process` | 입력만으로 결과 계산 |
| 기본 | 기존 사실에서 값 도출 | `derive` | 단순 계산을 `infer` | 결정적 도출에 사용 |
| 기본 | 외부 문자열·바이트 해석 | `parse` | 검증 없는 `convert` | 잘못된 형식을 거부 |
| 기본 | 표시용 표현 생성 | `format` | 저장 형식에 `format` | 사람 또는 UI 대상 표현 |
| 기본 | 저장·전송 인코딩 | `serialize` | 표시와 저장 형식 혼합 | 복원 가능한 형식에 사용 |
| 기본 | 저장·전송 형식 복원 | `deserialize` | 검증 없는 cast | 형식 검증 포함 |
| 기본 | 허용 표현을 정규형으로 통일 | `normalize` | 의미 변경에 `normalize` | 의미는 유지되어야 함 |
| 제한 | 대응하는 표현으로 이동 | `map` | 모든 변환에 `mapper` | source와 target이 명확할 때 사용 |
| 기본 | 단위·타입·표현 변경 | `convert` | 단순 field 복사 | 무엇에서 무엇으로 바뀌는지 드러냄 |
| 기본 | 규칙 위반 판정·수집 | `validate` | Boolean 하나에 `validate` | 오류·위반을 반환하거나 던짐 |
| 기본 | 한 조건의 Boolean 확인 | `check` 또는 긍정형 Boolean | 상태 변경을 숨기는 `check` | 부수 효과 없이 확인 |
| 제한 | 필요하면 상태를 만족시킴 | `ensure` | 읽기 전용 검증에 `ensure` | 멱등적인 보정이 실제로 있을 때만 사용 |
| 기본 | 여러 값을 기준으로 묶음 | `group` | 불명확한 `organize` | grouping key를 인자나 문맥으로 표현 |
| 기본 | 조건에 맞는 값만 선택 | `filter` | 단건 선택에 `filter` | collection 결과에 사용 |
| 기본 | 하나의 값 선택 | `select` | DB 조회가 아닌데 `query` | 선택 정책이 있을 때 사용 |

## 경계와 역할 명사

| 상태 | 표현 | 사용 조건 | 대체 기준 |
| --- | --- | --- | --- |
| 제한 | `Service` | 유스케이스 또는 여러 소유자의 흐름 조정 | 한 유스케이스면 `행동 + 대상 + Service`; 직접 동사 대신 명사화하지 않음 |
| 제한 | `Manager` | 자원의 전체 생명주기 관리 | 실제 자원이나 유스케이스 역할 |
| 제한 | `Handler` | 특정 request·command·event 한 종류 처리 | 입력 종류를 함께 표현 |
| 제한 | `Controller` | HTTP·UI·CLI 입력 경계 | framework 관례와 입력 대상 |
| 제한 | `Client` | 특정 원격 API·protocol 호출 | 외부 시스템 이름 포함 |
| 제한 | `Gateway` | 외부 subsystem의 고수준 통합 계약 | domain capability를 우선 |
| 제한 | `Repository` | domain object·aggregate 저장 경계 | 단순 key/value면 `Store` 검토 |
| 제한 | `Store` | session·document·key/value 저장 | 정본 domain 저장이면 `Repository` 검토 |
| 제한 | `Cache` | 재생성 가능한 비정본 저장 | 정본 저장에 사용 금지 |
| 제한 | `Factory` | 생성 전략을 캡슐화 | 함수 하나면 `create...` 사용 |
| 제한 | `Builder` | 단계적 조립과 중간 상태가 필요 | 단순 생성이면 `build...` 함수 |
| 제한 | `Provider` | 값·dependency·capability 공급 | 공급 대상을 이름에 포함 |
| 제한 | `Adapter` | 서로 다른 계약·형식을 연결 | package 문맥으로 충분하면 생략 |
| 제한 | `Mapper` | 명확한 source/target 대응 | 대상 쌍을 이름에 포함 |
| 제한 | `Validator` | 재사용되는 검증 규칙 집합 | 한 함수면 `validate...` 사용 |
| 제한 | `Policy` | 업무 결정을 내리는 규칙 집합 | 한 조건이면 구체적 rule 이름 |
| 제한 | `Strategy` | 같은 계약 아래 교체 가능한 알고리즘 | 구현 차이를 이름에 포함 |
| 제한 | `Scheduler` | 실행 시각·반복 정책 결정 | 실제 작업 실행은 `Worker` |
| 제한 | `Worker` | 전달받은 background 작업 실행 | queue·작업 대상을 표현 |

경계 타입의 기본 어휘:

| 상태 | 표현 | 소유 경계 |
| --- | --- | --- |
| 제한 | `Request`, `Response` | HTTP·message 전송 |
| 제한 | `Command`, `Query` | application 입력 |
| 제한 | `Event` | 이미 발생한 사실 |
| 제한 | `Entity` | identity와 영속 생명주기 |
| 제한 | `Result` | 명시적인 성공·실패 결과 계약 |
| 제한 | `Config` | 해석·검증이 끝난 구성 |
| 제한 | `Options` | 호출자가 선택적으로 조정하는 값 |
| 제한 | `Context` | 한 실행 범위에서 공유되는 문맥 |

`Request`와 `Command`처럼 경계 증거가 필요한 이름은 annotation, 생성 위치와 호출자를 확인한다. 증거가 없으면 확정하지 않는다.

## 금지하거나 제한하는 표현

| 상태 | 표현 | 문제 | 대체 방법 |
| --- | --- | --- | --- |
| 금지 | `thing`, `stuff` | 대상이 없음 | 도메인 대상 사용 |
| 제한 | `data`, `info`, `value`, `object` | 단독으로 의미가 부족함 | 실제 내용과 역할 사용 |
| 금지 | `util`, `helper` 단독 타입·파일명 | 소유 책임이 없음 | 소유 기능과 행동 사용 |
| 제한 | `common`, `shared` | 공유 이유와 소유자가 없음 | 공유하는 도메인 의미 사용 |
| 제한 | `process`, `processor` | 결과와 효과가 불명확함 | 관찰 가능한 결과 동사 사용 |
| 제한 | `handle`, `handler` | 입력 종류가 불명확할 수 있음 | request·event·command 대상 포함 |
| 제한 | `manager` | 만능 조정 타입으로 확장되기 쉬움 | 생명주기 전체를 소유할 때만 사용 |
| 제한 | `service` | 책임 없는 중간 계층이 되기 쉬움 | 유스케이스나 domain capability 사용 |
| 금지 | `Default`, `Impl` 단독 구현 구분 | 구현 차이를 설명하지 않음 | 전략·기술·외부 시스템 사용 |
| 제한 | `Base`, `Abstract` | 상속 이유를 설명하지 않음 | 공통 계약이나 template 역할 표현 |
| 제한 | `Model` | domain·transport·view 의미가 섞임 | 실제 경계 역할 사용 |
| 제한 | `Payload` | 내용과 경계가 불명확함 | event·request의 구체적 내용 사용 |
| 제한 | `do`, `execute`, `run` | 행동 대상과 결과가 없음 | 실제 domain 행동 사용 |
| 금지 | `and`, `with`, `using`으로 단계 연결 | 함수가 여러 책임을 숨김 | 결과 하나로 축약하거나 함수 분리 |
| 금지 | `new`, `old`, `temp`, 숫자 접미사 | 책임 대신 작업 상태를 이름에 남김 | 실제 역할·버전·수명 표현 |

금지는 framework가 생성하거나 외부 공개 계약이 강제하는 이름까지 무조건 변경하라는 뜻이 아니다. 강제 이름은 유지하고 새 내부 이름에서 확산을 막는다.

## 약어와 짝 이름

기본 허용 약어는 언어와 개발 문맥에서 널리 통용되는 `id`, `url`, `uri`, `http`, `api`, `db`, `io`, `ui`다. 대소문자는 언어 스킬을 따른다.

- domain 고유 약어는 같은 저장소에서 의미가 하나로 고정됐을 때만 추가한다.
- 한 범위에서 약어와 전체 단어를 섞지 않는다.
- 공개 API에는 팀 내부에서만 아는 약어를 새로 도입하지 않는다.
- 한 글자 이름은 매우 좁은 반복·수학·좌표 문맥에만 허용한다.

짝 이름은 다음 기본 쌍을 사용한다.

| 의미 | 선호 쌍 |
| --- | --- |
| 변환 방향 | `source` / `target` |
| 시간·범위 경계 | `start` / `end` |
| 변화 전후 | `previous` / `current` 또는 `before` / `after` |
| 계층 관계 | `parent` / `child` |
| 송수신 | `sender` / `recipient` |
| 최솟값·최댓값 | `minimum` / `maximum` |
| 활성·비활성 | `enable` / `disable` |
| 연결·해제 | `attach` / `detach` |

축약형 `min`·`max`는 수학식, UI 속성 또는 기존 공개 API 관례가 있을 때만 사용한다.

## 저장소·도메인별 어휘

이 문서는 여러 프로젝트에 적용할 전역 기본만 소유한다.

- 특정 저장소의 product·domain 용어는 그 저장소의 glossary나 `AGENTS.md`에 둔다.
- 특정 언어의 casing, package, file 이름은 언어 스킬에 둔다.
- framework가 강제하는 접미사와 annotation 이름은 해당 framework 스킬에 둔다.
- Woon 저장소 이름과 `repo://` 같은 고유 계약은 Woon 저장소 규칙에 둔다.

지역 규칙이 이 문서와 다르면 공개 계약과 실제 domain 의미를 우선하고, 차이를 전역 선호로 자동 승격하지 않는다.

## 어휘 추가·변경 절차

새 선호를 추가할 때 다음 항목을 한 행에 기록한다.

1. 상태: `확정`, `기본`, `제한`, `금지`, `폐기`
2. 상황: 어떤 입력·출력·경계에서 쓰는지
3. 선호 표현과 피할 표현
4. 선택한 표현이 약속하는 의미
5. 기존 항목과 충돌하거나 겹치는지

변경 절차:

1. 저장소 전체에서 기존 표현과 후보 표현을 검색한다.
2. 같은 뜻의 행은 새로 만들지 않고 기존 행을 갱신한다.
3. 더 구체적인 domain 용어라면 전역 문서 대신 해당 저장소에 둔다.
4. 공개 이름을 바꾸면 호출자, import, 직렬화, reflection과 저장 형식을 확인한다.
5. 폐기 표현에는 대체 표현과 호환 종료 조건을 정한다.
6. 대표 positive·negative 예시를 naming behavior eval에 추가한다.

사용자가 대화에서 선호를 변경하면 이 문서의 해당 행을 단일 정본으로 갱신한다. 이전 선호를 별도 중복 목록으로 남기지 않는다.
