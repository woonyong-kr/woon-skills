# 기술 블로그 승격 계약

## 목적

블로그는 채용 담당자에게 프로젝트를 판매하는 카드가 아니라, 다른 엔지니어가 특정 조건에서 판단을 재사용할 수 있는 글이다. 정본 전체가 아니라 독자 질문 하나에 필요한 claim만 선택한다.

## 구조

1. 결론: 어떤 조건에서 어떤 선택을 했는가.
2. 문제와 관찰: 규모, 실패 증상, 제약과 재현 조건.
3. 판단: 검토한 대안과 선택 기준.
4. 실행 또는 원리: 실제 identifier와 변경 경계.
5. 증거: code·test·측정·architecture 중 claim을 직접 증명하는 것.
6. 한계: 측정하지 못한 것, 팀·개인 경계, 적용되지 않는 조건.
7. 다음 질문: 별도 글로 분리할 후속 문제만 연결.

자기소개, 역할 요약 카드, 기술 stack 나열, 채용용 형용사로 시작하지 않는다. 프로젝트 전체를 한 글에 압축하지 않는다. 숫자는 metric context가 완전한 claim만 사용한다.

## Portfolio와의 차이

블로그는 `왜 이 판단이 맞았는가`를 설명한다. 개인 역할은 저자성과 한계를 밝히는 데 필요한 만큼만 쓴다. portfolio candidate의 성과 문장을 문단 제목으로 복사하지 않고, portfolio가 이 글을 상세 근거로 링크하게 한다.

architecture image는 경계·흐름·before/after를 prose보다 명확히 증명할 때만 넣는다. 공개 승인된 asset과 source provenance를 확인하고 앞 문장이 볼 질문, alt가 핵심 관계, 뒤 문장이 해석을 담당하게 한다.
