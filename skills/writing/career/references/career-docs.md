# 커리어 문서 작성 스킬 (career-docs)

> 2026년 KRAFTON AI Engineer 지원 문서 일체(이력서 사이트 · 커버레터 · 경력기술서 ·
> 블로그 24편)를 수십 회 반복 검수하며 확립한 기준. 모든 규칙에는 실패에서 배운 이유가 있다.

## 0. 대원칙 — 어길 수 없는 것

1. **검증 불가능한 주장은 쓰지 않는다.** 링크·코드·영상·제3자 기록으로 증명 못 하는 문장은
   본문 서술로 낮추거나 삭제한다. 삭제가 기본값이다.
   (실례: "메모리 풀 설계" → 실체가 Microsoft 오픈소스로 판명되어 철회.
   "다국어·DLC 대응" → 근거 없어 삭제. 저자 증명 불가한 기여 → 불릿에서 제외)
2. **주장 → 근거의 거리는 클릭 1회.** 불릿의 핵심 단어에 내부 상세 글을 링크하고,
   외부 실물(GitHub·YouTube·서비스)은 그 글 안에서 연다.
3. **숫자는 문서 전체에서 단 하나다.** 이력서·커버레터·경력기술서·블로그의 같은 사실은
   같은 숫자여야 한다. 하나라도 어긋나면 전부가 의심받는다.
4. **한계를 스스로 밝힌다.** "판매량은 공개 자료가 없어 쓰지 않습니다",
   "100%는 실전 정확도가 아니다" — 한계 명시가 나머지 주장의 신뢰를 만든다.
5. **팀 성과와 내 몫을 구분한다.** "5인 팀 프로젝트입니다. 그중 제 몫은 ~였습니다."
   면접에서 "네 몫이 뭐냐"는 반드시 나온다.

## 1. 페르소나 검증 체계 — 모든 문서의 관문

문서 초안이 나오면 아래 6인 페르소나로 검수하고 **표로 보고**한다
(페르소나 | 지적 | 조치). 전원 통과 전에는 완성이라 부르지 않는다.

| 페르소나 | 검증 질문 |
|---|---|
| 코치(취업 코치) | 독자가 제일 궁금해할 질문("왜 전직했나" 등)에 변명이 아닌 **당위**로 답하는가. 스토리가 상단에 있는가 |
| CTO | 첫 문장에 정보가 있는가. 증거 없는 형용사는 없는가. 클릭해서 검증하면 살아남는가 |
| 실무 엔지니어 | 팀 프로젝트에서 이 사람 몫이 분리되는가. 기술 용어가 정확한가 |
| 인사담당자 | 문서 형식(인사말·맺음·연락처)이 갖춰졌는가. 읽는 흐름이 한 번에 통하는가 |
| 압박면접관 | 과장·아부·검증불가 주장·오버스펙 의심 지점이 있는가 |
| 국어 감수 | 번역투·꾸민 어투·중복 단어·고아 줄바꿈·단어 중간 개행이 없는가 |

경위 설명(전직·공백 등)은 **논증하지 말고 언급만** 한다. 길게 설명할수록 변명으로 읽힌다.
당위 한 문장의 예: "PD가 된 것도 더 큰 문제를 풀기 위해서였고, 한 번도 개발자가 아닌 적은 없었습니다."

## 2. 문체 규칙 (jojoldu 기준 분석에서 확립)

- 불릿은 **명사로 끝난다**: 개발 · 구축 · 운영 · 설계 · 개선 · 도입 · 리드 · 구현 · 제거 · 차단 · 해소 · 수료 · 제작
- 숫자는 볼드 + 괄호 보조: `INSERT 병목 제거 (2,751 → 591,429 ops/sec)`
- 성과 수치 3종 세트: 절대값 + 배수 환산 + 측정 조건 ("1M 행, 3회 중앙값")
- **금지 어휘**: "저는"(주어 생략이 기본) · "그대로 가져와" · "늘 그래 왔듯" ·
  "책임졌습니다"(수동 → "이끌었습니다") · "여기/클릭/참고" 링크 텍스트 · 지어낸 내부 용어(예: 골든셋)
- 같은 키워드가 두 불릿에 나오면 하나를 지운다. 태그는 **실제 기술 스택만** — 개념어·장식 태그 금지
- 소개글 문단은 하나가 한 축(정체성 → 현장 → 현재), 문단 끝 고아 줄("니다."만 남음)은 끝맺임 축약으로 해소

## 3. 문서별 규격

### 3-1. 이력서 불릿
```
소제목 | 불릿 1 | 불릿 2 | 태그: A · B
```
- 불릿당 링크 최대 3개, 링크는 주장을 대표하는 명사구에
- 역할 줄은 `·` 단위로 짧게 — 중복 역할(총괄 PD면 '프로젝트 관리'는 중복) 제거

### 3-2. 소개글 (3문단 표준형)
1. 정체성 한 문장 (헤드라인과 같은 사람으로 읽히게)
2. 현장 증거 한 문장 (대표 성과 + 전환 계기)
3. 현재 한 문장 (지금 하는 일 = 지원 직무와 연결)

### 3-3. 커버레터 (A4 1장, 순수 편지)
- 구조: 큰 이름 → 연락처 블록 → 날짜 → "안녕하세요" → 문단 6개 → "감사합니다 / OOO 드림"
- 회색 박스·섹션 헤더·아이콘 금지 — 문단으로만. 숫자는 문장 안에 녹인다
- 기승전결: 정체성+직무 일치(두괄식) → 현장 서사 → 전환 당위+기술 증명 → 하고 싶은 일(JD 표현 회수)
- JD 인용체 금지("공고의 인재상에서 '…'라는 문장을 읽고") — 내 말로 풀어 사실 진술로
- **AI 냄새 삭제 목록**: 검증 안내 푸터, "모든 수치는 ~로 확인 가능", 과한 볼드, 이모지, 대시 구분 문구

### 3-4. 경력기술서 (A4 1장)
- **재직 경력만** (교육 과정 프로젝트는 포트폴리오 몫)
- 이력서 화면과 같은 문법: 회사 헤더(이름·기간·요약 한 줄) → 프로젝트 역순 2단
  (왼쪽: 이름·역할·기간 / 오른쪽: 부제·소제목별 불릿·#태그)
- 개발 기여와 리드 기여를 소제목으로 분리
- 줄바꿈 품질: 역할 단위를 nowrap 으로 묶어 단어 중간 개행 방지, 넘치는 불릿은 축약

### 3-5. 기술 블로그 글 (포트폴리오의 근거 페이지)
고정 골격: **결론 두괄식 → 문제(규모·조건 포함) → 판단 → 실행 → 숫자 → 확인할 수 있는 것 → 한계**
- 첫 1~3문장은 독자의 문제를 구체적으로. 자기소개·일반론으로 시작 금지
- **추상 개념 도입 직후 다이어그램**, **성능 주장 직후 실측 증거 이미지** (성능 글 4~12장)
- 이미지 캡션 없음 — 앞 문장이 예고하고 뒷 문장이 해석한다
- "확인할 수 있는 것" 절: 실제 파일 경로를 적되 **레포를 열어 실재를 확인한 경로만**
- "한계" 절 필수. 기대 출력과 실측 로그를 구분해 표기 (돌리지 않은 것을 돌린 것처럼 쓰지 않는다)
- 유튜브는 본문에서 재생되게 임베드, 시작 시점(t=초) 지정 가능하면 지정

## 4. 검증 절차 — 발행 전 기계적으로 실행

```bash
# 내부 링크 ↔ 실제 문서 슬러그 전수 대조 (불일치 0이어야 함)
# GitHub 저장소: git ls-remote --heads <url>  (실패하면 링크 금지)
# YouTube 공개 여부: https://www.youtube.com/oembed?url=<영상주소>&format=json
# 수치 주장: 링크된 레포를 clone 해 grep 으로 원본 존재 확인
#   (예: "시나리오 116개" → evals/results.md 의 116/116 실재 확인 후 통과)
```
- 외부 사실(스토어 얼리액세스 여부 등)은 실제 페이지를 열어 확인 후 기술
- 문서 간 수치 교차 대조: 이력서 = 커버레터 = 경력기술서 = 블로그

## 5. 동의·권리 경계

- 회사 내부 자료는 **동의받은 용도 범위 안에서만** 사용한다. 용도가 다르면 넣지 않고,
  사용자가 요청해도 동의 범위 확장 여부를 먼저 확인한다
- 팀 저장소는 이름 변경·이력 재작성·강제 푸시 금지. 개인 미러는 `--mirror`로 저자 보존,
  README 에 출처 명시
- 타인 코드(회사 엔진, 오픈소스)를 내 것처럼 쓰지 않는다 — "엔진을 제가 만들었다고
  말하지 않는 이유"를 글에 적는 수준까지

## 6. 작업 워크플로우

1. **연구 먼저**: JD 원문 · 본인 기록(노션·vault·레포) · 레퍼런스 블로그 분석. 문서 형식은 그다음
2. **초안**: 위 규격대로. 사용자의 실제 문장이 있으면 그것을 뼈대로 (지어낸 서사 금지)
3. **페르소나 루프**: 표 보고 → 사용자 피드백 → 수정. "자연스럽지 않다"는 피드백은
   문장이 아니라 구조(임무 과적·논증화·추상어)의 문제일 가능성부터 의심
4. **기계 검증**: §4 전부
5. **전달**: PDF 는 A4 1장 엄수(넘치면 여백·행간·문장 축약 순서로), 문서 세트는 같은
   헤더·서체·톤으로 통일. 산출물 숫자가 바뀌면 다른 문서도 같이 갱신
