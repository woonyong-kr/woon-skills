# 기술 글쓰기 기준

## 문장과 어조

- 한국어 설명은 합쇼체를 기본으로 하고 한 문단에는 주장 하나만 둔다.
- 결론이나 관찰을 먼저 쓰고 그 이유와 증거를 뒤에 연결한다.
- 기술 이름, class·method·field·option은 source 표기를 유지한다.
- 이모지, AI 공동저자 문구, 감탄, 동기부여 문장과 근거 없는 과장을 제거한다.
- `대부분`, `빠르다`, `안전하다` 같은 판단에는 범위, 조건이나 측정 근거를 붙인다.

## 구조 선택

모든 글에 고정 목차를 강제하지 않는다. 글이 해결하는 질문에 필요한 section만 다음 순서에서 고른다.

1. 독자가 관찰할 문제나 목표
2. 실행 조건과 최소 사례
3. 실제 결과 또는 확인 가능한 현상
4. 원인과 개념
5. 개선 또는 적용 절차
6. 반례, 실패 조건과 한계
7. 판단 기준과 다음 질문

section 하나는 질문 하나에 답한다. 같은 질문을 설명·예제·요약이라는 이름으로 반복하지 않는다. 병렬 비교가 세 항목 이상일 때만 표를 고려하고, 인과와 순서는 문단·번호 목록·diagram으로 표현한다.

## 제목과 계층

- 제목은 대상과 핵심 질문이 드러나는 짧은 명사구로 쓴다.
- H1은 독립 문서에서 한 번만 사용한다. H2 다음에 H4처럼 heading level을 건너뛰지 않는다.
- 긴 문서는 heading hierarchy를 목차의 정본으로 삼는다. 수동 목차는 대상 renderer에서 anchor를 검증할 수 있을 때만 만든다.
- 새 내용은 문서 끝이 아니라 선행 개념 뒤이면서 처음 필요해지는 section 앞의 가장 이른 위치에 넣는다.

## 코드, 결과와 그림

- code 앞에는 무엇을 볼지, 뒤에는 어떤 결과가 원인을 증명하는지 쓴다.
- 실행한 결과와 예상 결과를 구분한다. 실행하지 않은 출력을 실제 결과처럼 만들지 않는다.
- 한 단계에서 바뀌는 조건을 최소화하고 before·after identifier를 일치시킨다.
- 그림은 prose보다 관계를 더 짧고 정확하게 설명할 때만 사용한다. code·memory·call·exception 흐름은 `$diagram`의 Mermaid 계약을 따른다.

## 근거와 한계

- 구현 사실은 code·manifest·test·실행 결과에, 외부 사실은 가능한 한 공식 출처에 연결한다.
- 수치에는 환경, 입력, 횟수와 측정 방법을 기록한다.
- 단순화한 설명은 적용 범위와 깨지는 조건을 함께 남긴다.
- summary에는 본문에서 증명하지 않은 주장을 추가하지 않는다.

## 저장 형식 경계

이 문서는 범용 본문 품질만 소유한다. frontmatter field, 폴더 경로, 공개 여부와 canonical ID는 대상 저장소나 archive adapter가 소유한다. `woon-knowledge` archive body에는 frontmatter와 H1을 넣지 않으며, 독립 Markdown에 임의의 Woon metadata를 추가하지 않는다.
